<objective>
Implement RMS speech sync (FLORA-04): the answer-state path where Jetson drives
light brightness in lockstep with TTS playback. Compute a downsampled RMS
envelope from the TTS WAV (stdlib `wave`+`audioop`, no numpy), normalize to
base..peak duty (D-08), and stream brightness frames to light channels 0-10 over
HTTP via `MCUClient.set_channels` on a wall-clock timer started at playback
dispatch, offset by `flora.speech.hdmi_latency_offset_ms` (HDMI buffer lag, D-07).
Random sparks on peaks add texture (D-08). The streamer cancels immediately on
`tts_finished` or barge-in (D-09).

This replaces the generic answer-state stub from plan 03 with the real RMS path.

CRITICAL WIRING (RESEARCH Open Q2, RESOLVED): the WAV bytes never travel through
the event bus — `tts_started`'s payload is `{"text":"(streaming)"}` (no WAV), and
the WAV is synthesized PER-CHUNK inside the streaming consumer (`_consumer`,
`Orchestrator.py:2888`) and played immediately via
`to_thread(tts._play_wav_bytes_sync, wav)` (~2878/2903/2931). A FloraController on
the event queue can therefore NEVER see those bytes. So this plan adds an explicit
Orchestrator edit (Task 3): `_consumer` calls `flora_controller.feed_speech_wav(wav)`
at the SAME instant it dispatches each chunk's playback. That makes WAV a
GUARANTEED input feeding the RMS path per-chunk, keeping D-07 single-timer sync and
matching the existing chunked playback (a per-reply single envelope would desync
from chunked playback — do NOT use that). The non-streaming `/speak` path (Silero
plays internally, WAV not exposed) is the ONLY degraded path — it falls back to a
generic `attentive`-style pulse with no precise sync; document that.

Purpose: the cinematic voice-reactive light that makes the installation feel alive.
Output: RMS envelope + feed_speech_wav intake + frame streamer in flora.py, the
per-chunk feed wired into Orchestrator's consumer, FLORA-04 test green.
</objective>
