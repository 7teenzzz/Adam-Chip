# Phase 31: Audio Input Tuning Panel - Context

**Gathered:** 2026-06-08
**Status:** Ready for planning

<domain>
## Phase Boundary

Построить единую UI-панель настройки ВХОДНОГО аудио-тракта (mic → DSP → OWW/ASR) с реальным серверным DSP, живым мониторингом и пресетами. Цель — дать оператору инструмент, которым он на месте давит паразитные частоты, выставляет фильтры под акустику зала и калибрует чувствительность wake-word, СЛЫША ровно тот сигнал, который слышит модель.

Панель включает:
- **Ползунок громкости входа** — управляет уже существующим `media.audio.input_gain` (ALSA capture + pulse source), который применяется на каждом старте (Phase 30, durable across reboot).
- **Графический эквалайзер** — интерактивная кривая поверх существующего FFT-виджета спектра (Phase 21A). Перетаскиваемые полосы = реальный серверный biquad-каскад, применяемый к захваченному PCM ДО OWW и ASR. Подавление паразитных частот реально влияет на распознавание.
- **Пресеты фильтров** — создание / сохранение / редактирование / удаление, хранятся в `System/Config.json` (единый конфиг).
- **Линия OWW-порога** — горизонтальная перетаскиваемая линия на эквалайзере, работает как ползунок `wake_word.threshold`, с живым оверлеем текущего score.
- **Кнопка «слушать микрофон»** — лёгкий стрим post-EQ сигнала в браузер клиента для тестирования.
- **Тумблеры** — мастер вкл/выкл всего входного DSP + индивидуальный тумблер на каждую подстройку (каждая полоса EQ, HPF, gain) для A/B-диагностики вклада каждой ступени.

**Out of scope:**
- Миграция на PipeWire — отдельная Phase 32 (панель должна работать и на текущем pulse, и после свапа без переделки — DSP в Python, не в звуковом сервере).
- Смена VLM на cosmos — Phase 33.
- ESP-микрофон — вход остаётся local USB (WebCamera).
- Подбор КОНКРЕТНЫХ значений фильтров/порогов под зал — это runtime-тюнинг через готовую панель, не задача сборки.
- Выходной TTS-DSP (HPF/компрессор/лимитер на ESP-динамик) — уже сделан в Phase 29, не трогаем.

</domain>

<decisions>
## Implementation Decisions

### DSP-архитектура
- **D-01 (Q1=A):** Эквалайзер — СЕРВЕРНЫЙ Python DSP (biquad-каскад, scipy/numpy), применяется к захваченному PCM в точке чтения микрофона ДО раздачи в OWW и ASR. UI только рисует/редактирует кривую; коэффициенты считаются на бэке и hot-reload'ятся. Браузерный-only EQ отвергнут: он не давит частоты для модели (цель не достигается) и создаёт расхождение «слышишь ≠ что слышит модель». Существующий 1-pole `media.audio.vad_hpf_hz` (220 Гц) ОБОБЩАЕТСЯ в первую полосу этого каскада — не дублировать фильтрацию.
- **D-02:** WYSIWYG-инвариант: один и тот же post-DSP сигнал идёт в OWW, в ASR И в браузерный монитор. Никаких отдельных трактов «для прослушивания» vs «для модели».
- **D-03:** Fail-safe: при любой ошибке DSP или невалидном пресете тракт откатывается на сырой PCM (bypass), голосовой цикл НЕ должен молчать из-за EQ. Безопасный дефолт = мастер-тумблер можно выключить и получить нынешнее поведение (только legacy gain + 1-pole HPF, либо чистый passthrough).

### Тумблеры (новое требование)
- **D-04:** Двухуровневые тумблеры. (1) Мастер: весь входной DSP вкл/выкл одним переключателем (мгновенный bypass → сырой захват). (2) Индивидуальные: каждая подстройка (каждая полоса EQ, HPF, makeup/gain-стадия) имеет собственный enabled-флаг. Назначение — A/B-диагностика: выключи любую ступень, услышь/измерь её вклад в реальном времени через монитор. Каждый флаг — в Config.json рядом со своим параметром.

### Хранение и конфиг
- **D-05 (Q2):** Пресеты эквалайзера живут в `System/Config.json` (единый конфиг, hot-reloadable), НЕ в отдельном файле. Структура: массив пресетов (имя + полосы + флаги) + ссылка на активный пресет. CRUD из панели идёт через существующий `/api/config`/tuning-механизм с hot-reload. Валидация — pydantic-модели в `System/adam/tuning.py` (как остальной tuning-блок). Config-First соблюдён: ни одного числа в коде.

### Монитор-стрим
- **D-06 (Q3=A):** Стрим микрофона в браузер — сырой PCM 16-bit 16 kHz по WebSocket, отдаётся POST-EQ. Браузер играет через Web Audio API (AudioWorklet). Opus отвергнут: lossy-кодек красит ровно те частоты, что диагностируешь; 256 кбит/с по LAN/localhost/AnyDesk — несущественно. Отдельный WS-эндпоинт (не SSE — SSE занят `audio_level` под виджет спектра). Half-duplex mute НЕ трогаем — монитор это прослушка входа, а не TTS-выход; инвариант `safety.half_duplex_mute=true` остаётся.
- **D-07:** Опциональный тумблер «pre/post EQ» в мониторе для живого A/B-сравнения кривой (слушать вход до и после DSP). Желателен, но не блокер — если режет сроки, выносится в follow-up slice.

### Wake-word калибровка
- **D-08 (Q4):** Горизонтальная линия на эквалайзере = ползунок `wake_word.threshold` (НЕ VAD-порог). Поверх — живой оверлей текущего OWW-score (переиспользовать поток score из `_vad_loop`/OWW-движка), чтобы видеть, как реальные срабатывания соотносятся с порогом, и тащить линию под них.

### Claude's Discretion
- Конкретная топология biquad-каскада (число полос, тип секций: peaking/shelf/HPF/LPF, порядок) — определит планирование/исследование. Базис: параметрический EQ с настраиваемыми f0/Q/gain на полосу + крайние HPF/LPF.
- Точка врезки DSP: `Orchestrator._vad_loop` (где сейчас `_apply_vad_hpf`) либо `mic_reader.py` local-mic путь — выбрать так, чтобы один обработанный буфер шёл и в OWW, и в ASR, и в монитор (D-02).
- Технология рендера кривой EQ на фронте (canvas/svg поверх существующего spectrum-виджета Phase 21A) и протокол перетаскивания полос.
- Формат WS-фреймов монитора (чистый PCM vs PCM+маркеры RMS/score) и механизм backpressure при медленном клиенте.
